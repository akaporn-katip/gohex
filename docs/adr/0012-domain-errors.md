# DomainError in the kernel; the split between domain and infra errors drives retry semantics

The kernel ships DomainError{Code, Message} (wrappable, errors.Is/As-friendly); each domain defines its own sentinel rules (e.g. ErrInsufficientStock). The distinction is enforced by machinery, not convention: the command bus and REST edge map a DomainError to a 4xx response or a rejection integration event (e.g. PaymentFailedV1) and never retry it — a business rejection is a fact sagas compensate on. Any other error is infrastructure: retried with backoff, then dead-lettered. A handler leaking a raw error therefore gets retry semantics, the safe default. Rejected a predefined error taxonomy (frozen API, endless Conflict-vs-BusinessRule debates) and plain-convention errors (the bus mechanically needs the retry/no-retry split).
