# Consumer-side span names carry the consumer and the fact, not just the destination

Consumer spans are named `consume <group> <messageType>` (o11y.Subscriber) and projection spans `project <projection> <messageType>` (o11y.ProjectionHook); producer spans stay `publish <topic>`. The OTel messaging conventions say a span name SHOULD be `{operation} {destination}` but explicitly permit a system-specific format provided it is documented — it is, in the o11y package doc comment and here. Rationale: in an async-only system (ADR-0008) one fact on one topic is consumed by every service integrating on it, so `consume tenancy.events` renders four fan-out consumers as four identical waterfall rows; the consuming service lives in the resource and the fact in `gohex.message.type`, and a waterfall shows neither without a click per row. The consumer group is the only disambiguator present in the data at the point the span starts, and the convention of naming groups `<service>.<projection>` makes it name both the service and the read model it feeds; adding the message type answers "which fact" in the same glance, which matters because one projection applies many kinds of event. Cardinality is bounded and knowable: consumer groups and message types are both compile-time sets declared in wiring code and contract types, not user input, so span-name cardinality is (groups × types) per topic — the same order as the handler count the service already has. Names degrade one field at a time (`consume <group>`, then `consume <topic>`) so an unnamed group or a typeless message still yields a locatable span. Every semconv-shaped attribute stays (`messaging.destination.name`, `messaging.consumer.group.name`, `messaging.message.id`), joined by `messaging.operation.name`/`messaging.operation.type`, so tooling that groups by destination or operation is unaffected and only the human-facing name changed; `gohex.message.type` also stays, because it is the framework's own vocabulary and existing queries filter on it. Rejected: leaving the name spec-shaped and telling operators to click each row (the trace is the readability product — a trace nobody can read is not observability); putting the service name in the span name (it is already the resource, and would be redundant everywhere except fan-out); and adding the aggregate or message ID to the name (unbounded cardinality, and `messaging.message.id` already carries it).
