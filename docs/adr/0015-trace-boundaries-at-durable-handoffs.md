# Trace boundaries at durable hand-offs: continue on synchronous consume, link on polled work

A hand-off consumed synchronously — the broker subscriber, the command consumer, the saga runner — continues the originating trace: the consumer span is a child of the producer's context carried in the envelope metadata (o11y.Subscriber). A hand-off that lands in a durable store and is later picked up by a polling worker ("work the list": tick, claim a batch, act) starts a NEW trace whose span carries an OpenTelemetry link back to the originating span context (o11y.StartLinked), and stamps the origin traceparent onto everything it produces under the `gohex.origin.traceparent` metadata key (o11y.OriginMetadata), so the causal chain stays queryable one hop further on. Rationale: a worklist item waits on a business-paced tick, is retried independently, and is batched with unrelated items — continuation would make trace duration report poll lag as latency, inherit a sampling decision taken minutes earlier in another service, attach late spans to an already-exported trace, and leave batch health (tick duration, batch size, error rate) with no sensible parent; links are what OTel defines for exactly this shape. Continuation remains available for the near-real-time tailing pollers (projection CatchUp/InboxReader, sub-second lag, not business-paced) via o11y.ContinueTrace() on the projection hook — the default there is still a linked new trace, so the rule holds unless a service opts out deliberately. The mechanism needed no new plumbing: eventstore.Repository.Save already stamps whatever trace context is on the ctx, so a worker's choice of ctx decides everything downstream; only o11y gained link helpers, keeping OpenTelemetry out of every other module (ADR-0009). Rejected: full continuation as the default (one honest-looking trace, dishonest timings), and carrying links in the event/message envelope as a first-class field (Metadata already transports cross-cutting context, ADR-0005).
