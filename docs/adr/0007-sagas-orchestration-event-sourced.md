# Sagas: orchestration-first, saga instances are event-sourced streams

The framework ships a saga orchestrator: an explicit state machine per workflow (e.g. OrderFulfillmentSaga) that reacts to integration events, issues commands, and runs compensations — chosen over pure choreography (flow exists nowhere, compensation smeared across services); docs will also show one small choreographed flow to teach when an orchestrator is overkill. A saga instance persists as an event-sourced stream like any aggregate: received events and decisions (CommandRequested) are appended, state rehydrates by replay, and outgoing commands ride the existing relay (ADR-0003) so decide-and-send is one atomic append. Rejected a second state-row+outbox machinery (two persistence models to keep crash-safe) and delegating to Temporal (outsources the feature the library exists to provide; noted in docs as the heavy-production alternative).
