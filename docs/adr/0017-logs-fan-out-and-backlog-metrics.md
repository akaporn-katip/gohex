# Logs fan out to stdout and OTLP; metrics are the backlogs only the framework can see

`o11y.Init` now installs all three OpenTelemetry signals over the same OTLP/HTTP endpoint: the trace exporter it always had, a `LoggerProvider`, and a `MeterProvider`. Logs FAN OUT rather than move — the default `slog` handler writes the same JSON line to stdout as before (trace_id/span_id as attributes, byte-for-byte the format downstream collectors and `kubectl logs` already parse) and, in the same `Handle` call, bridges the record to the OTLP logger, where the SDK stamps the trace and span ID from the context onto the record itself, so a backend joins log to trace without parsing a string (`o11y.NewSlogHandler`, `o11y.Fanout`). Each sink gets its own copy of the record and one sink's failure never costs another its line; `Fanout` is the whole mechanism, and `NewLogHandler` is untouched, so anything wrapping it keeps working. Metrics are deliberately narrow: the only instruments are the BACKLOGS behind the framework's durable hand-offs — `gohex.relay.lag` (store head minus relay checkpoint), `gohex.projection.lag` (source head minus projection checkpoint, per projection and per source, because a projection's store runner and inbox runner fall behind independently) and `gohex.inbox.depth` (inbox head minus reader checkpoint) — registered as asynchronous gauges so the callback costs one cheap query per collection and an idle service costs nothing (`o11y.WatchRelayLag`, `WatchProjectionLag`, `WatchInboxDepth`). Rationale for the split: traces already answer "how long did this hand-off take, and did it fail", and a spanmetrics connector at the collector derives command and query latency and error rate from spans we already export, so a histogram in the framework would be a second, disagreeing source of the same truth; no trace can answer "how much work is waiting RIGHT NOW", because the events that are behind have no span yet — the relay being nine thousand events behind is invisible in a trace store and is exactly the alert an async-only system (ADR-0008) needs, since every read-model staleness complaint and every "the other service never reacted" resolves to one of these three numbers. Every one of them is the same subtraction, head minus checkpoint (ADR-0003, ADR-0006), which is why one internal sampler with three names and three attribute sets covers all of them. Both positions are supplied by the caller as `o11y.Position` functions, keeping OpenTelemetry out of the relay, projection and event-store modules (ADR-0009): checkpoints already have a port, so `o11y.CheckpointPosition` adapts any `eventstore.CheckpointStore`, but HEADS have none — neither `eventstore.Store` nor `projection.Inbox` reports "the last sequence you hold" — so today a service passes a closure (for eventstore-postgres, `select coalesce(max(global_seq), 0) from events`). Adding a `Head` method to those two ports is the follow-up that turns each call into a one-liner; it is a port change affecting every implementation, so it belongs in `eventstore`/`projection` minor releases rather than being forced into an o11y release as an awkward seam or, worse, as a relay-internal instrument the service cannot see. `Config.WithoutExporter` and an unset endpoint keep their existing meaning for all three signals — propagation, the metadata hook, stdout logging and the gauge registrations all still work, they just reach no collector, because the global no-op meter never invokes a callback — and the `shutdown` Init returns flushes and stops trace, log and metric providers in turn, continuing past a failure so a stuck trace exporter cannot cost the metrics their final export. Rejected: sending logs only over OTLP (a collector outage would leave an operator with no logs at all, and `kubectl logs` is the first thing anyone reaches for); leaving logs to a node-level file scraper (it works, but the trace correlation survives only as a parsed string attribute, and the whole point is a first-class join); exposing a Prometheus `/metrics` endpoint instead (a second protocol and a second scrape path to operate, when the collector already accepts OTLP from every service); command, query and handler latency histograms (duplicates the spans, multiplies cardinality by every command name, and dashboards would have to pick a winner when the two disagree); and instrumenting lag inside the relay and projection modules (OpenTelemetry in every module, contradicting ADR-0009, and the gauge would still need a head query those modules do not have).
