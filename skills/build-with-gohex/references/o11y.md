# Observability: one trace across the async hops

Canonical examples in the checkouts:

- `gohex-example/ordering/cmd/ordering/main.go` — the full wiring: init first,
  wrapped broker, bus middlewares.
- `o11y/` — small surface; read `o11y.go`, `broker.go`, `cqrs.go`,
  `log.go`, `backlog.go` directly.
- `o11y/o11y_test.go` — every propagation guarantee, including
  `TestWeaveEndToEnd` (one trace: edge → store → relay → broker → consumer).
- `o11y/telemetry_test.go` — the log fan-out and the backlog gauges, including
  `TestInitExportsAllThreeSignals` (traces, logs and metrics all reach the
  collector, flushed by the shutdown `Init` returns).
- `o11y/worker_test.go`, `o11y/projection_test.go` — the durable-hand-off
  boundary (ADR-0015).
- `gohex-example/ordering/internal/app/notifier.go` — the canonical polling
  worker: batch span per tick, linked trace per row.

## The idea

Trace context survives *through the event store*: the repository stamps the
current span context into event metadata on save; the relay carries it into
the broker envelope; the subscriber wrapper extracts it on the far side. The
result is one trace from the HTTP edge to the last service in the flow —
without any handler touching a span.

## Wiring checklist (all four pieces, or the trace breaks)

1. **`o11y.Init` first** in main, before anything that emits spans; defer the
   returned shutdown (flush; it drains traces, logs and metrics). Configured
   per service name; exports all three signals over OTLP/HTTP to the endpoint
   in `OTEL_EXPORTER_OTLP_ENDPOINT` or `Config.OTLPEndpoint` — the example
   stack ships HyperDX in `docker-compose.yml` to view them.
2. **Wrap the broker**: `o11y.Publisher(...)` / `o11y.Subscriber(...)` around
   the Kafka client, and use only the wrapped values downstream. Publisher
   injects context only if absent (the store-stamped context wins); subscriber
   continues the trace and marks error spans.
3. **Bus middlewares**: `o11y.CommandMiddleware()` / `o11y.QueryMiddleware()`
   on the buses. Domain-error rejections are *not* span errors — only
   infrastructure failures are (`TestCommandMiddlewareRejectionIsNotSpanError`).
4. **Logs join traces**: `Init` already installs this — the default slog logger
   writes the JSON line to stdout (with `trace_id`/`span_id` attributes) *and*
   bridges the same record to OTLP, where the trace/span IDs are first-class
   fields on the record (ADR-0017). Use `slog.Default()` / the `*Context`
   methods (`slog.InfoContext(ctx, …)`) — a log call with no ctx has nothing
   to correlate. Reach for the parts only to add a sink of your own:
   `o11y.NewSlogHandler` builds the stdout+OTLP pair, `o11y.Fanout` is the
   mechanism, `o11y.NewLogHandler` the trace-stamping wrapper alone.

Stdout is not vestigial: it is what `kubectl logs` and compose show when the
collector is down, and its format is pinned — do not "simplify" it away.

`o11y.Inject`/`o11y.Extract` exist for carrying context over any other edge
you build (custom metadata maps).

## Span names: who is doing what (ADR-0016)

The framework names spans after the actor and the fact, not just the
destination — a fan-out of five services on one topic must not render as five
identical waterfall rows:

```
publish <topic>                     publish tenancy.events
consume <group> <messageType>       consume billing.billing_views tenancy.lease_started
project <projection> <messageType>  project billing_views tenancy.lease_started
command <commandName>               command tenancy.start_lease
```

Consequences for your service: name consumer groups `<service>.<projection>`
(the group is the only disambiguator present when the span starts), and keep
both groups and message types compile-time constants — they are span names now,
so a user ID in either is a cardinality incident. If a dashboard or alert
queries by attribute rather than name, the semconv attributes
(`messaging.destination.name`, `messaging.consumer.group.name`,
`messaging.operation.*`, plus `gohex.message.type`) are all still there.

## Polling workers: link, don't continue (ADR-0015)

A trace continues across a hand-off the service consumes *synchronously*
(broker subscriber, command consumer, saga runner). It does NOT continue
across a hand-off that lands in a table and waits for a worker's tick — a
pending list, a worklist. There the trace would report poll lag as latency
and inherit a stale sampling decision. Instead:

1. **Capture at write time.** The projection handler that inserts the pending
   row stores the causing envelope's metadata (`msg.Metadata`, or
   `projection.Meta.Metadata` for own events) in a metadata column. It carries
   trace context only, never business data.
2. **Tick span.** `o11y.StartBatch(ctx, "<work> batch", len(rows))` — its own
   root trace, the home for batch size, tick duration and failures.
3. **Row span.** `o11y.StartLinked(batchCtx, "<work>", row.Metadata)` — a new
   root trace linked to the origin AND to the tick. Dispatch the command with
   that context: `Repository.Save` stamps it onto the events, and the origin
   rides along as `gohex.origin.traceparent`, so the next service can link one
   hop further (`o11y.LinkFrom`, `o11y.OriginMetadata`).

Projection runners are pollers too: pass
`projection.Config{Observe: o11y.ProjectionHook()}` to `NewCatchUp`/
`NewInboxReader` so every apply is traced (linked by default;
`o11y.ProjectionHook(o11y.ContinueTrace())` is the deliberate opt-out for
sub-second tailing).

## Backlog metrics: the question traces cannot answer (ADR-0017)

`Init` installs a MeterProvider exporting OTLP alongside the traces. The
framework's only instruments are the backlogs behind its durable hand-offs,
because work that is backed up has no span yet — a trace store cannot tell you
the relay is nine thousand events behind:

| Gauge | Meaning | Wire with |
|---|---|---|
| `gohex.relay.lag` | store head − relay checkpoint | `o11y.WatchRelayLag` |
| `gohex.projection.lag` | source head − projection checkpoint, per projection *and* source (`store` / `inbox`) | `o11y.WatchProjectionLag` |
| `gohex.inbox.depth` | inbox head − inbox reader checkpoint | `o11y.WatchInboxDepth` |

Register one per worker the service runs, in the composition root after `Init`.
Each takes two `o11y.Position` funcs — head and checkpoint — and returns an
`Unwatch` you only need if the worker stops at runtime. Checkpoints already
have a port, so `o11y.CheckpointPosition(checkpoints, "<name>")` is the whole
processed side. Ask the runner for the name rather than retyping it:
`Projection.StoreCheckpoint()` and `Projection.InboxCheckpoint()` name a
projection's two cursors; the relay's is the name you gave it.

**Heads come from the ports.** `eventstore.Store` and `projection.Inbox` both
report `Head` — the last position they hold, 0 when empty — so wire it
straight through: `o11y.PositionFunc(store.Head)`, `o11y.PositionFunc(inbox.Head)`.
No SQL in main.go. A hand-written closure is only for a log this framework's
ports do not describe; if you catch yourself writing `max(global_seq)` in a
composition root, the port already answers it.

Do **not** add command/query/handler latency or error-rate instruments. Those
are derived from the spans you already export (a spanmetrics connector at the
collector); a second source of the same number is a dashboard argument waiting
to happen. Sampling is cheap — these are asynchronous gauges, so the callback
runs once per collection, not per event — but the query behind a head must stay
cheap too: an indexed `max()`, never a count over a scan.

With `Config.WithoutExporter` or no endpoint configured, registration still
succeeds and samples nothing, so tests and collector-less laptop runs wire the
gauges exactly like production.

## Verify

After wiring a new service, run the system (`task up`, `task demo`) and check
the trace for one order in HyperDX: it must be a single trace spanning
edge → ordering → saga → your service's consumer → its relay's published
facts. A broken parent-child link means one of the four pieces above is
missing or you bypassed a wrapped component.

Work that a polling worker performs is deliberately a SEPARATE trace: check
that it carries a link back to the request's trace (and that the request's
trace links forward to it), not that it is one trace.

Then check the other two signals, because both fail silently: a log line the
service emitted must be findable in the backend *and* in `docker compose logs`
/ `kubectl logs`, and clicking its trace ID must land on the trace above (if
it does not, the log call had no ctx). For metrics, stop the relay or a
projection runner, append a few events, and watch its lag gauge climb — a
gauge that is flat at 0 while a worker is down means the head closure is
lying, not that the system is healthy.

## Tests you must ship (non-negotiable)

If you add a custom edge (anything that moves context via metadata), pin it
the way `o11y/o11y_test.go` does: inject/extract round-trip, and
consumer-side continuation (child span shares the trace ID). For standard
wiring, the framework's own tests cover propagation — your job is the
end-to-end check above, not re-testing the lib.

Same rule for metrics: `o11y/telemetry_test.go` pins the gauges themselves, so
the only thing worth testing on your side is a head closure you wrote — point
it at the memory or dockerless test store and assert it reports the last
appended sequence. A head query that silently returns 0 turns every lag alert
into a lie.
